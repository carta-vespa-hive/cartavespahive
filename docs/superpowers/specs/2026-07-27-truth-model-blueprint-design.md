# Truth-Model Blueprint Editor Design

## Summary

Carta Vespa Hive's first product slice is a truth-model-first diagram editor for non-technical users. A user names a system, records its components, relationships, labels, and supporting evidence, and receives a clean editable blueprint. The blueprint is a visual projection of structured facts; it is not the source of those facts.

This slice implements the **Structure** stage of CVH's Structure → Expand → Inspect method. Futuristic illustrated cutaways, image generation, material rendering, model calls, and AI inspection are expressly out of scope.

## Goals

- Let a non-technical user describe a system without writing JSON or diagram syntax.
- Store the system as typed, portable truth data with stable identifiers.
- Render that truth as a light, legible, editable blueprint.
- Keep layout and other visual choices separate from system facts.
- Warn about incomplete labels, missing evidence, and dangling relationships while preserving the user's work.
- Export the blueprint as versioned JSON that does not depend on CVH's UI.

## Non-goals

- Generating futuristic, biomorphic, photorealistic, or illustrated cutaways.
- Calling an image model, language model, or external diagram service.
- Inferring components or evidence on the user's behalf.
- Collaborative editing, accounts, cloud persistence, comments, or revision history.
- SVG, PNG, or PDF export in this slice.
- Implementing the Expand or Inspect stages beyond local structural validation warnings.

## Considered approaches

1. **Normalized truth model plus separate view state — chosen.** Facts remain stable when the diagram moves or changes style; validation and JSON export are direct.
2. **Canvas objects with embedded metadata — rejected.** Position, shape, and drawing-library details would become the de facto data model and make portability fragile.
3. **Prompt or free-text document — rejected.** It is approachable at entry time but cannot reliably identify dangling relationships, missing evidence, or stable component identity.

## User experience

The editor presents one guided workspace in plain language:

1. **Name the system.** The user enters a required system name and an optional short purpose.
2. **Add components.** Each component receives a stable internal ID, a user-facing name, a concise functional label, an optional description, and zero or more evidence references.
3. **Connect components.** The user chooses a source and destination component, adds a relationship label, and attaches evidence.
4. **Add evidence.** Evidence is a short statement classified as an observation, source, or assumption. A source may include an optional URL or citation note.
5. **Edit the blueprint.** The system renders components as labeled nodes and relationships as directional connectors. Editing a name or label updates truth data. Moving a node updates only view state.
6. **Review warnings.** An always-visible validation summary points to incomplete items without deleting data or blocking continued editing.
7. **Export JSON.** The user downloads a portable, versioned blueprint containing separate `truth` and `view` sections.

The interface follows the current clean diagram-foundry direction: warm light paper, dark ink, restrained functional color, modern sans-serif and mono metadata, clear selection states, and no decorative spectacle. The current Vite/React single-page structure remains the application foundation.

## Data model

The portable document has two independent sections:

```ts
interface BlueprintDocument {
  schema: "cvh-blueprint";
  version: "1.0";
  truth: BlueprintTruth;
  view: BlueprintView;
}

interface BlueprintTruth {
  system: {
    id: string;
    name: string;
    purpose?: string;
  };
  components: ComponentTruth[];
  relationships: RelationshipTruth[];
  evidence: EvidenceTruth[];
}

interface ComponentTruth {
  id: string;
  name: string;
  label: string;
  description?: string;
  evidenceIds: string[];
}

interface RelationshipTruth {
  id: string;
  fromComponentId: string;
  toComponentId: string;
  label: string;
  evidenceIds: string[];
}

interface EvidenceTruth {
  id: string;
  kind: "observation" | "source" | "assumption";
  statement: string;
  reference?: string;
}

interface BlueprintView {
  componentPositions: Record<string, { x: number; y: number }>;
  viewport?: { x: number; y: number; zoom: number };
}
```

Truth fields describe what the system is. View fields describe only how the current blueprint is arranged. Node position, viewport, color, size, connector routing, selection, and panel state must never be treated as evidence or structural facts.

IDs are generated by CVH and remain stable across edits and exports. Relationships and evidence use those IDs rather than array positions or display names. Renaming a component therefore does not break its relationships.

## Application boundaries

The future implementation should preserve the current Vite/React app and separate responsibilities into small typed modules:

- **Truth model:** creates and updates `BlueprintTruth` without importing React or rendering code.
- **Validation:** accepts truth data and returns deterministic warnings; it never mutates the document.
- **View state:** stores component positions and viewport independently from truth.
- **Blueprint projection:** converts truth plus view state into editable nodes and connectors.
- **Editor UI:** provides plain-language forms and selection controls for non-technical users.
- **Serialization:** exports `BlueprintDocument` as versioned JSON without UI-only state.

React owns the editing session, but domain operations stay in typed library modules under `src/lib/`. The visual blueprint should use browser-native React/SVG capabilities unless implementation planning proves a dependency necessary; no diagramming library is assumed by this design.

## Data flow

1. A form action produces a typed truth-model command such as add component, update label, or add relationship.
2. The command returns a new truth document while preserving stable IDs.
3. Validation runs against the new truth document and returns warnings.
4. The blueprint projection reads truth plus view state and rerenders nodes and connectors.
5. Dragging or viewport changes update view state only and do not rerun truth commands.
6. Export serializes the latest truth and view sections into versioned JSON.

There is no model-generated or inferred content in this flow. Every fact and piece of evidence comes from the user.

## Validation behavior

Validation is deterministic and non-destructive. Each warning has a stable code, human-readable message, affected entity ID, and field when applicable.

Required warnings:

- `component.missing-label` when a component label is blank after trimming.
- `component.missing-evidence` when a component has no valid evidence reference.
- `relationship.missing-label` when a relationship label is blank after trimming.
- `relationship.missing-evidence` when a relationship has no valid evidence reference.
- `relationship.dangling-source` when `fromComponentId` does not identify an existing component.
- `relationship.dangling-target` when `toComponentId` does not identify an existing component.
- `evidence.missing-statement` when an evidence statement is blank after trimming.
- `evidence.invalid-reference` when an entity references an evidence ID that does not exist.

Warnings appear both in a summary and beside the affected editor control or blueprint element. A dangling relationship may remain in truth data so the user can repair it, but it renders in a warning style without pretending to connect to a valid component. Warnings do not block JSON export; incomplete work remains portable.

## Portable export

The first export format is UTF-8 JSON with the `.cvh-blueprint.json` suffix. It includes the exact `BlueprintDocument` structure above and no runtime-only React state. Export must be deterministic for the same document apart from optional file naming.

## Concrete example: AI support workflow

System: **Customer-support AI workflow**

Evidence:

- `ev-intake` — observation: "All requests enter through the support form."
- `ev-triage` — source: "Triage policy v2, section 3."
- `ev-review` — source: "Sensitive replies require human approval."

Components:

- `intake` — name: "Support form"; label: "Capture request"; evidence: `ev-intake`
- `triage` — name: "Triage model"; label: "Classify request"; evidence: `ev-triage`
- `review` — name: "Human reviewer"; label: "Approve sensitive reply"; evidence: `ev-review`

Relationships:

- `intake` → `triage`; label: "Submit for classification"; evidence: `ev-intake`
- `triage` → `review`; label: "Escalate low confidence"; evidence: `ev-review`

The blueprint shows three labeled nodes and two directional connectors. Dragging "Human reviewer" changes its position only. Removing `review` while retaining the second relationship produces `relationship.dangling-target` until the user reconnects or removes that relationship.

## Error handling and accessibility

- Invalid actions preserve the last valid document and show a plain-language inline message.
- All editing actions must be available without dragging; positions can be reset or adjusted through keyboard-accessible controls.
- Blueprint elements expose their names, labels, relationship direction, and warning state to assistive technology.
- Color never carries validation or selection meaning by itself.

## Acceptance criteria

1. A user can create and rename one system without editing JSON.
2. A user can add, edit, and remove components with names, functional labels, descriptions, and evidence references.
3. A user can add, edit, reconnect, and remove directional relationships with labels and evidence references.
4. A user can add, edit, and remove observation, source, and assumption evidence.
5. The app renders every valid component and relationship as an editable blueprint element.
6. Changing truth data updates the blueprint; moving a node changes view state without changing truth data.
7. Missing labels, missing evidence, invalid evidence references, and dangling endpoints produce the specified deterministic warnings.
8. Warnings identify the affected entity, appear in the editor and blueprint, preserve user data, and do not block export.
9. Exported `.cvh-blueprint.json` files contain separate versioned `truth` and `view` sections, exclude UI-only runtime state, and parse as standard JSON outside CVH.
10. The editor remains usable by keyboard and does not rely on color alone.
11. The slice contains no model calls, image-generation claims, illustrated-cutaway generator, or Expand-stage visual rendering.
12. `npm run typecheck` and `npm run build` pass, and the primary create/edit/validate/export flow is verified in the browser.

## Scope decision

This is one bounded product slice: author trustworthy system structure, project it into an editable blueprint, validate incompleteness, and preserve it portably. Any request for automatic diagram invention, decorative rendering, futuristic cutaways, generative imagery, or visual inspection belongs to a later separately designed slice and must not expand this implementation.
